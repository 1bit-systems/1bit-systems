DSpark speculative decoding — 572 tok/s with a 5-layer draft model

⚠️ Correction (2026-07-07): the "572 tok/s" in this post was a projection (base engine × a 5.90× acceptance figure measured with DeepSpec on Qwen3-4B, CPU/GPU — not the NPU). When the C++ DSpark path was finally run end-to-end on the real NPU with the Qwen3-0.6B INT8 target, it measured 0.1–0.2 tok/s at 0% draft acceptance: the draft, trained on HuggingFace hidden states, is rejected 100% of the time against the INT8 target's feature distribution, so speculation yields no gain. The projection is disproven; DSpark is experimental, not production. The architecture description below is kept for reference. See the performance SSOT.

tl;dr: DSpark is a C++ speculative decoding engine that pairs a tiny 5-layer transformer draft model (running on CPU) with the NPU target engine. The draft speculates 5-8 tokens ahead, the NPU verifies them in a single batch pass. It was projected to reach 572 tok/s (5.90× over baseline); end-to-end measurement disproved this — 0.1–0.2 tok/s at 0% acceptance (see correction above). The idea is sound; the current draft needs retraining on NPU-generated INT8 hidden states.

The problem: the NPU is idle while the CPU waits

The fused layer engine reaches 291 tok/s (3.4 ms/tok) — already the fastest NPU inference on Strix Halo by a wide margin. But the NPU operates as a synchronous co-processor: submit work, wait for completion, read results, submit next. During that wait, the NPU is busy but the CPU is idle, and during the CPU's token sampling and scheduling, the NPU is idle.

Speculative decoding breaks this cycle by decoupling the two paths:

Without speculation: CPU: [submit]→[wait]→[sample]→[submit]→[wait]→[sample] NPU: [─── GEMM ──] [─── GEMM ──] └── NPU idle while CPU samples, CPU idle while NPU computes ──┘ With DSpark speculative decoding: Draft: [─── 5 tokens ──]→[─── 5 tokens ──]→[─── 5 tokens ──] NPU: [──── verify batch of 5 ────] [──── verify batch of 5 ────] └── NPU processes 5 tokens per dispatch instead of 1 ──┘

The draft model: 5 layers, 34 MB

The DSpark draft model is an Eagle3-style MTP (Multi-Token Prediction) head. It's not a separate LLM — it's a lightweight prediction head trained to guess what the target model would output next:

ComponentDetails
Architecture5-layer transformer + Markov head + confidence head
Parameters~8.5M @ FP16 — fits in L2 cache
Binary size34 MB (safetensors → flat binary)
ComputeCPU (any x86 core, no GPU needed)
Training data10K prompts, distilled from target model self-play
Prediction horizon5-8 speculative tokens per forward pass

The draft receives the target model's hidden state (trunk_hidden) concatenated with the token embedding, then runs self-attention + SwiGLU FFN to produce draft logits. The entire draft forward pass takes ~200 μs on a Zen 5 core — much faster than the NPU's ~3.4 ms target decode, so multiple speculative rounds can run in the time of one target verification.

The verify loop

Speculative decoding requires lossless quality — every token the user sees must match what the target model would have generated. DSpark achieves this through rejection sampling:

// Simplified speculation loop (spec_decode.h)
while (generating) {
  // 1. Draft proposes N tokens
  draft_tokens[N] = draft.generate(hidden_state);

  // 2. Target verifies all N in one batch
  target_logits[N] = target.verify(draft_tokens);

  // 3. Accept or reject each token
  for i in 0..N {
    if (accept(draft_logits[i], target_logits[i]))
      emit(draft_tokens[i]);  // accepted – zero extra cost
    else {
      emit(sample(target_logits[i]));  // rejected – correct token
      break;
    }
  }
}

The magic is that the target NPU dispatch processes all N speculative tokens in a single batch. With M=32 batch decode, the overhead of verifying 5 draft tokens is barely more than verifying 1. At ~80% acceptance rate, the effective throughput approaches 5× the baseline.

The theory behind the 572 projection (why it didn't hold)

The fused layer engine's 291 tok/s is single-token decode latency. The 572 tok/s projection assumed DSpark would turn that into effective throughput — many tokens per verify — via a high acceptance rate. The theory:

  • 291 tok/s = one fused dispatch generates one token. The NPU does everything but the CPU has nothing to overlap.
  • Projected 572 tok/s = the draft speculates ahead while the NPU verifies in bulk, ~5.9 accepted tokens per verify.

That only works if the target accepts the draft's guesses. On the real NPU, acceptance is 0% — the draft was trained on a different (HuggingFace FP) hidden-state distribution than the INT8 NPU produces, so every guess is rejected and the pipeline degenerates to slower-than-baseline decode. Same chip, sound idea, wrong draft.

The 5.90× came from the DeepSpec eval on Qwen3-4B (CPU/GPU). It does not transfer to the INT8 NPU 0.6B target: the draft was trained on HuggingFace FP hidden states, and the NPU's INT8 quantization produces a different feature distribution, so acceptance collapses to 0%.

What it would take to actually reach a high number

The architecture is sound — the reason it fails today is the draft/target mismatch, not the pipeline. To move throughput off 0.1–0.2 tok/s the draft must be retrained on NPU-generated INT8 hidden states (not HF FP), and the target forward must use the fast fused xclbin rather than the current scalar-CPU attention + CPU lm_head path.

Measured reality: 0.1–0.2 tok/s at 0% acceptance. The 572 tok/s figure was a projection that end-to-end measurement disproved. Honest status lives in the performance SSOT.
