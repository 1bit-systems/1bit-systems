The fused layer engine — one xclbin call per transformer layer

tl;dr: The fused layer engine combines QKV projection, attention, output projection, gate+up, SiLU, and down projection into one xclbin call. No CPU attention, no intermediate buffer syncs. Result: 291 tok/s (3.4 ms/tok) in a 38 KB binary.

The bottleneck that killed v12

The v12 engine ran at 97 tok/s (10 ms/tok). Fast — but every transformer layer required 6 separate xclbin dispatches: Q_proj, K_proj, V_proj, O_proj, Gate+Up, Down. Each dispatch carried ~50 μs of ioctl overhead. Across 28 layers and 32 batch tokens: 2,688 ioctl calls per decode step.

The NPU spent more time in driver overhead than actual computation.

One call to rule them all

The fused xclbin takes a single design — design_full_layer.xclbin (416 KB) — and executes the entire transformer layer in one NPU-side pass:

┌──────────────────────────────────────────┐ │ One xclbin dispatch │ ├──────────────────────────────────────────┤ │ QKV Projection (3 GEMMs) │ │ → Q/K norms + RoPE │ │ → Attention (NPU-side) │ │ → Output projection │ │ → Gate + Up projection │ │ → SiLU activation │ │ → Down projection │ │ → Residual add │ └──────────────────────────────────────────┘

The NPU receives input activations, streams them through all 6 matrix operations, applies norms and attention internally, and returns the layer output. No CPU round-trips between operations. No BO syncs. No ioctl overhead per-GEMM.

How the fused dispatch works

The xclbin is compiled from AMD's MLIR-AIE toolchain using n1_core_i8_v2.py — the same INT8 MLIR generator that produces the per-GEMM xclbins, but with the full layer graph stitched together in Chess:

// Pseudo: fused layer Chess kernel layout
for each position p in batch {
  // Phase 1: QKV
  Q[p] = GEMM(hidden[p], W_Q);
  K[p] = GEMM(hidden[p], W_K);
  V[p] = GEMM(hidden[p], W_V);

  // Phase 2: Attention
  K[p] = rope(K[p], p);
  Q[p] = rope(Q[p], p);
  scores[p] = softmax(Q[p] · KV_cache / sqrt(d));
  attn_out[p] = scores[p] · KV_cache;

  // Phase 3: Output + FFN
  O[p] = GEMM(attn_out[p], W_O);
  gate[p] = GEMM(O[p], W_gate);
  up[p] = GEMM(O[p], W_up);
  hidden[p] = GEMM(silu(gate[p]) * up[p], W_down);
}

All data flows through NPU-local SRAM. The host only sees the input push and output read — everything else is on-device.

The weight format challenge

The fused xclbin expects weights in AMD's proprietary Q4NX chunk format — a tiled layout where weights are distributed per-column and per-row (row_chunk = block*16 + group*4 + patch*2 + row_in_patch). The original fused xclbin attempt (Update 20) hit deadlock because it replicated chunks identically across columns instead of indexing per-tile.

The fix was reconstructing the correct packing schedule from AMD's qwen3_model.py::_projection_stream_from_schedule — reading real Q4NX chunks straight out of model.q4nx with no dequant/requant cycle.

Batch decode: the force multiplier

The fused layer alone is fast. But at M=1, the NPU is still 99% idle. M=32 batch decode runs 32 token positions through the fused layer in one pass, amortizing the single ioctl call across all of them:

Batch-32 decode:
  1 fused xclbin dispatch → 32 tokens processed
  NPU time: ~106 ms for 32 tokens
  Effective: 3.4 ms/tok

38 KB binary

The final binary is smaller than the previous 74 KB daemon despite doing more per call. Static linking + stripped symbols + zero Python runtime paths. The entire inference engine fits in a single Slack message.

3.4 ms/tok. 38 KB. One xclbin call per layer. The NPU does the entire transformer in one pass — no CPU attention, no intermediate syncs, no Python anywhere.
