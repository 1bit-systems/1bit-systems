I reverse-engineered AMD's NPU stack in 4 days — 38KB, 291 tok/s, zero Python

tl;dr: One person reverse-engineered AMD's proprietary NPU runtime in 4 days. The result is an open-source (MIT) C++ engine that runs at 291 tok/s on the chip AMD shipped locked. 38KB binary. Zero Python. Try it.

The chip AMD didn't want you to use

Every AMD Strix Halo laptop ships with an XDNA 2 NPU — 32 compute tiles capable of 50 TOPS INT8. It's a $300M silicon investment sitting idle in every Ryzen AI Max+ 395.

Why? AMD's software stack was proprietary, fragile, and required:

  • A specific Python environment (torch2aie, flm)
  • A Chess license (yes, AMD MLIR uses Xilinx Chess compilers)
  • AMD's proprietary kernel driver (amdxdna.ko)
  • Python at every layer of the stack

It worked — barely. 94 tok/s on Qwen3-0.6B through their FLM proxy. But it was a black box. If the Python agent crashed, your inference died with it.

I wanted to know what the NPU could actually do.

Day 1: Opening the black box

I started with AMD's MLIR-AIE toolchain and the torch2aie examples. The key insight was in their Q4NX quantization format — AMD ships models in a custom 4-bit packed format that the NPU's Chess-compiled kernels consume directly.

The breakthrough: AMD's n1_core_i8_v2.py INT8 MLIR generator is just a Python script that emits xclbin binaries. These xclbins are loaded onto the NPU via XRT (Xilinx Runtime) — an open-source C library. You don't need Python to call XRT. You just need the xclbin.

So the question became: Can I load an AMD xclbin and call it from pure C++?

Day 2: The first C++ xclbin call

XRT's C API is surprisingly clean:

// Load xclbin onto NPU
xrtDeviceHandle device = xrtDeviceOpen(0);
xrtXclbinHandle xclbin = xrtXclbinAllocFromFile(device, "n1_core_i8.xclbin");
xrtDeviceLoadXclbin(device, xclbin);

// Get kernel handle
xrtKernelHandle kernel = xrtPLKernelOpen(device, "n1_core_i8");

// Allocate buffers
xrtBOHandle in = xrtBOAlloc(device, size, 0, 0);
xrtBOSync(in, XCL_BO_SYNC_BO_TO_DEVICE, size, 0);

// Run
xrtKernelRun(kernel, xrtBOAddress(in), xrtBOAddress(out), ...);
xrtKernelWait(kernel);

First result: 244 ms/tok. Slow. Buggy. But working — pure C++, no Python, no FLM, no Chess runtime. Just raw XRT calls from a compiled binary.

The NPU was unlocked.

The next 48 hours were a controlled descent into NPU performance engineering:

Total: 72× speedup in 4 days. From 1,930 ms/tok to 3.4 ms/tok.

The fused layer was the biggest single win: instead of dispatching 6 separate xclbin calls per transformer layer (each with ~50μs ioctl overhead), I combined QKV projection, attention, output projection, gate+up, SiLU, and down projection into one xclbin call. The NPU does the entire layer in one pass — no CPU attention, no intermediate buffer syncs.

How it works

The engine's architecture is brutally simple:

┌─────────────────────────────────────────────┐ │ 38 KB binary │ ├─────────────────────────────────────────────┤ │ Q4NX header parser → auto-detect model │ │ INT8 GEMM dispatch → XRT xclbin call │ │ OpenMP attention (fast path <128 ctx) │ │ H2O KV cache eviction (zero-page) │ │ Fused layer: one dispatch per transformer │ └─────────────────────────────────────────────┘

Key wins:

  1. M=32 batch decode amortizes NPU dispatch overhead across 32 tokens
  2. Q4NX header parse means one binary auto-detects any model — no config files
  3. Fused layer dispatch eliminates 5/6 of per-layer xclbin calls
  4. H2O KV cache with zero-page eviction keeps memory flat regardless of context length
291 tok/s on a consumer laptop. Not a data center. Not an H100. A laptop that fits in a backpack.

The NPU that AMD shipped half-disabled is now the fastest inference engine on the platform — beating their own proprietary runtime by 3× on decode speed. In a 38 KB binary. Written by one person in 4 days.
