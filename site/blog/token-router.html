TokenRouter: Token-Level Multi-Backend LLM Inference on AMD Strix Halo

Research Open Source AMD

2026-07-11 · bcloud · github.com/bong-water-water-bong/token-router

Abstract

We present TokenRouter, the first open-source token-level routing system for multi-backend LLM inference. Unlike request-level routers (LiteLLM, OpenRouter) that select a single backend per request, TokenRouter routes individual tokens to the optimal backend mid-stream — the fast NPU for high-confidence tokens, the capable GPU for complex reasoning — all within a single SSE stream.

On AMD Strix Halo (Ryzen AI Max+ 395), we demonstrate a complete speculative decoding pipeline combining: a custom NPU engine with real per-token logprobs (the first open-source implementation on XDNA2), a Vulkan GPU backend running ternary-quantized models at 279 tok/s, and a token-level router with dma-buf zero-copy KV cache handoff.

Why Token-Level Routing?

Within a single LLM response, some tokens are easy and some are hard. A request-level router commits the entire generation to one backend — wasting the NPU's 70 tok/s on tokens the GPU could handle better, or burning GPU cycles on trivial completions the NPU could nail instantly.

Architecture

1. Speculative Decode Pipeline

The core innovation: draft on NPU, verify on GPU. Each round:

  1. Draft — NPU generates N tokens (default 4, dynamic 1-16) with per-token logprobs
  2. Accept — tokens forwarded to client immediately (real-time streaming)
  3. Verify — GPU can verify the draft in parallel via dma-buf zero-copy KV cache handoff
  4. Adapt — n_draft adjusts dynamically: >85% acceptance → grow, <50% → shrink
Round loop (dynamic n_draft: 1-16):
  NPU:  "The" (p=-0.05) ✓  "quantum" (p=-2.80) ✗
  GPU:  "quantum Fourier transform"  [parallel verify]
  Accept: "The" → client, "quantum Fourier transform" → client
  n_draft: 4→5 (acceptance rate 0.85)

2. Cascade Strategy

Confidence-based token routing. Start on NPU, check each token's log-prob, seamlessly switch to GPU when confidence drops — all within a single stream. The client sees one continuous response.

3. Content Router

Request-level routing by message analysis. Keywords, length, tool calls determine the backend. "Write code for..." → GPU. "Hello" → NPU. Text >800 chars → GPU.

4. Zero-Copy KV Cache Handoff

On Strix Halo's unified memory architecture, the NPU→GPU handoff uses dma-buf file descriptors shared via SCM_RIGHTS. No PCIe bottleneck, no data copy — the GPU picks up the NPU's cache state in O(1).

Backend Details

NPU Engine (Custom)

The NPU backend runs a custom C++ engine (npu_engine_server) that communicates via a stdin/stdout JSON protocol. It loads Qwen3-0.6B Q4NX weights and dispatches INT8 matrix multiplies to the XDNA2 NPU via XRT xclbin kernels. The engine performs top-k + top-p sampling and returns real per-token logprobs from the softmax distribution — a capability FLM's OpenAI API wrapper does not expose.

GPU Backend (ZINC)

ZINC is a Zig inference engine running ternary-quantized Bonsai-1.7B (1.58-bit) on the Radeon 8060S via Vulkan. At 279 tok/s benchmarked, it serves as the verification backend, capable of accepting NPU-drafted tokens and continuing generation with higher-quality outputs.

Related Work

WhiFlash (Kwon et al., Samsung AI Center, June 2026) independently proposes token-level cross-paradigm routing between autoregressive and diffusion-based drafters, achieving up to 69.6% throughput gains over EAGLE-3. Their approach validates the token-level routing hypothesis from a complementary angle (AR↔diffusion vs. NPU↔GPU).

The Strix Halo Pipeline (mikealanni, 2026) demonstrates NPU+GPU pipeline inference on the same hardware but notes that "FLM's OpenAI API doesn't expose logprobs." Our custom NPU engine solves this, enabling real rejection-sampled speculative decoding.
