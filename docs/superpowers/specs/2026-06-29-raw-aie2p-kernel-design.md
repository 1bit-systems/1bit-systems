# Raw AIE2P VLIW Kernel Pipeline — Correct-First Design

## 1. Problem Statement

The NPU (Strix Halo, 8-column XDNA2, firmware 1.1.2.65, XRT 2.21.75) achieves 82 GFLOPS on open-source GEMM kernels (via IRON/MLIR) vs. a 31 TFLOPS Chess compiler reference — a **378× gap**. The gap is in compiler scheduling: Chess produces tightly software-pipelined VLIW code while the open-source stack emits padded, sub-scheduled instructions. The goal is to build a pipeline that produces **correct, functional GEMM kernels at any M×K×N** on the raw DRM path, then iterate toward Chess-level performance.

## 2. System Architecture Overview

The pipeline has four layers, each with verified outputs feeding the next:

```
Layer 4: Raw VLIW Assembler (Python)  → AIE2P instruction bytes (.text section)
                     ↓
Layer 3: Chess/Peano VLIW Extractor   → AIE2P instruction bytes (from compiler .o)
                     ↓
Layer 2: Instruction Buffer Builder    → insts.bin (header + commands + BD descriptors)
                     ↓
Layer 1: DRM Submitter                 → NPU execution via DRM ioctls
```

**Phase 1 covers Layers 1–2** — get a parameterised GEMM generator producing correct output.
**Phase 2 covers Layer 3** — Chess VLIW integration.
**Phase 3 covers Layer 4** — raw VLIW assembler.
**Phase 4** — DeepSpec speculative decoding integration using the NPU-accelerated draft model.

This spec covers Phases 1–3 with verified facts only.

## 3. Layer 1: Submission Infrastructure

### Existing verified path

`npu_raw_submit.c` at `/home/bcloud/npu-sandbox/npu-infer/src/npu_raw_submit.c` is the proven DRM path. It:
1. Opens `/dev/accel/accel0`
2. Creates a hardware context with `DRM_IOCTL_AMDXDNA_CREATE_HWCTX`
3. Allocates GEM buffers (input, weights, output, instruction buffer) — coherent DMA buffers
4. Writes instruction buffer into `inst_buf` GEM object
5. Submits job with `DRM_IOCTL_AMDXDNA_EXEC_CMD` (sets `cu_idx`, `buffer`, `buffer_size`, `prop_count`, `prop_args`)
6. Waits for completion via `DRM_IOCTL_AMDXDNA_WAIT_CMD`

### What stays the same

- DRM ioctl sequence
- GEM buffer allocation (4K-aligned)
- `cu_idx` for tile targeting

### What changes

- `inst_buf` content is generated by Layer 2 instead of being a hard-coded array
- A correctness loop: run kernel → read output GEM buffer → compare against numpy/CPU reference

## 4. Layer 2: Instruction Buffer Format (Verified)

### 4.1 Overview

From reverse-engineering `fresh_insts.bin` (8400 bytes, 224 commands) and `libgemm_instrs.bin` (17120 bytes, 312 commands), the instruction buffer is a flat byte array:

```
[16-byte header] [command 0] [command 1] ... [command N]
```

Round-trip verified: parse → rebuild → byte-for-byte match on `fresh_insts.bin`.

### 4.2 Header (16 bytes, 4 words)

| Offset | Field | `fresh_insts.bin` | `libgemm_instrs.bin` |
|--------|-------|-------------------|----------------------|
| 0 | word0 | `0x06040100` | `0x48000000` |
| 4 | word1 | `0x00000108` | `0x00000000` |
| 8 | word2 | `0x000000e0` (224) | `0x00000138` (312) |
| 12 | word3 | `0x000020d0` (8400) | `0x00002170` (8560) |

**`fresh_insts.bin` header decoding:**
- `word0 = 0x06040100`: bit-packed. `instr_compiler.py` interprets as `(num_mem_tile_rows << 24) | (num_cols << 16) | (num_rows << 8) | version` → num_mem_rows=6, num_cols=4, num_rows=1, version=0
- `word1 = 0x00000108`: flags/config — consistent across IRON-generated buffers.
- `word2 = num_ops` (command count)
- `word3 = total_size` (header + body bytes)

**`libgemm_instrs.bin`** has a different header (`0x48000000`) — likely a different generator (libgemm.so vs IRON). Its `total_size` field (8560) does **not** match file size (17120), suggesting a different semantics.

### 4.3 Tile Addressing (Verified)

From addresses used in BLOCKWRITE and DDR_PATCH commands:

```
tile_base = (col << 24) | (row << 16)
```

Examples:
- `0x0601d000`: col=6, row=1, offset=0xd000
- `0x0001d000`: col=0, row=1, offset=0xd000
- `0x0201d044`: col=2, row=1, offset=0xd044
- `0x0c01d124`: col=12, row=1, offset=0xd124

Offset `0xd000` = DMA BD descriptor queue area (within tile address space).
Offset `0x80000` = Core program memory (from `xaie2psgbl_params.h`).
Offset `0xD0000` = Module data memory (128-bit wide).
Offset `0xC0100` = DMA status/control registers.

### 4.4 Command Types (Verified, `fresh_insts.bin`)

| Opcode | Name | Size | Count | Description |
|--------|------|------|-------|-------------|
| `0x00` | WRITE | 24 B | 64 | Write a 32-bit value to a tile address |
| `0x01` | BLOCKWRITE | 48 B | 64 | Write 32-byte BD descriptor to BD queue at address |
| `0x03` | MASKWRITE | 28 B | 16 | Write with bitmask (core control registers) |
| `0x80` | SYNC | 16 B | 16 | DMA synchronization barrier (col, row, direction) |
| `0x81` | DDR_PATCH | 48 B | 64 | Runtime-patch a BD's buffer_addr_lo with GEM DMA address |

### 4.5 WRITE Command (24 bytes)

| Offset | Size | Field |
|--------|------|-------|
| 0 | 1 | opcode (0x00) |
| 1 | 1 | pad (0x00) |
| 2 | 2 | pad |
| 4 | 4 | pad |
| 8 | 4 | addr_lo (target tile address, lower 32 bits) |
| 12 | 4 | addr_hi (target tile address, upper 32 bits) |
| 16 | 4 | value (32-bit value to write) |
| 20 | 4 | opSize (always 24) |

### 4.6 BLOCKWRITE Command (48 bytes)

| Offset | Size | Field |
|--------|------|-------|
| 0 | 1 | opcode (0x01) |
| 1 | 1 | pad (0x00) |
| 2 | 6 | pad |
| 8 | 4 | addr (BD queue address = tile_base + 0xd000 + i*32) |
| 12 | 4 | opSize (always 48) |
| 16 | 32 | BD payload (8 words × 4 bytes) |

### 4.7 BD Payload Format (8 words, 32 bytes)

From `fresh_insts.bin` BD queue entries at rows 0 and 1:

| Word | Field | Example | Description |
|------|-------|---------|-------------|
| 0 | buffer_length | `0x00002000` (8KB), `0x00020000` (128KB) | Size of the DMA buffer in bytes |
| 1 | buffer_addr_lo | `0x00000000` (patched) | Lower 32 bits of buffer DMA address — **runtime-patched by DDR_PATCH** |
| 2 | buffer_addr_hi | `0x00000000` | Upper 32 bits of buffer DMA address |
| 3 | control | `0x02000000` (1D), `0x04000000` (2D) | DMA control: bits [25:24] = dimensionality |
| 4 | dma_config_0 | `0xc80001ff`, `0xc2000fff` | DMA stride/fetch configuration |
| 5 | dma_config_1 | `0x020000ff`, `0x0200003f` | DMA step/burst configuration |
| 6 | dma_config_2 | `0x0010ffff`, `0x00000000` | DMA second-dimension stride |
| 7 | lock_acq_rel | `0x02000000` | Lock acquire/release for DMA completion |

Control word decoding (`fresh_insts.bin`):
- `0x02000000` = 1D DMA (single linear buffer)
- `0x04000000` = 2D DMA (with row stride)
- bits [31:26], [23:0] need further decoding

dma_config_0 patterns:
- `0xc80001ff`: burst_len = 0x1ff, addr_step = 0xc8 (200 words)
- `0xc2000fff`: burst_len = 0xfff, addr_step = 0xc2
- `0xc0000000`: null BD (no DMA)

### 4.8 DDR_PATCH Command (48 bytes)

| Offset | Size | Field |
|--------|------|-------|
| 0 | 4 | opcode+pad (0x81 + padding) |
| 4 | 4 | opSize (48) |
| 8 | 12 | reserved |
| 20 | 4 | action (0 = replace) |
| 24 | 4 | patch_addr (target address in instruction buffer = BD_queue_base + 4) |
| 28 | 4 | reserved |
| 32 | 4 | arg_idx (0=A, 1=B, 2=C buffer) |
| 36 | 4 | reserved |
| 40 | 4 | arg_plus (byte offset within buffer) |
| 44 | 4 | reserved |

From `fresh_insts.bin` DDR_PATCH patterns:
- `arg_idx=0` (A buffer): patched into BDs in rows 0, with `arg_plus` incrementing by `0x200000` (2MB per column tile)
- `arg_idx=1` (B buffer): patched into BDs in rows 1 and 6, with `arg_plus` incrementing by `0x80000` (512KB) per tile
- `arg_idx=2` (C buffer): patched into BDs in row 6, with `arg_plus` offset `0x80` bytes per BD

The patch target address is the BD's `buffer_addr_lo` field (word 1) within the instruction buffer's BLOCKWRITE payload. The firmware replaces `buffer_addr_lo` with `gem_addr + arg_plus` at submission time.

### 4.9 MASKWRITE Command (28 bytes, opcode 0x03)

Used in `fresh_insts.bin` for core control register programming. Format needs further reverse-engineering from the 16 instances.

### 4.10 SYNC Command (16 bytes, opcode 0x80)

| Offset | Size | Field |
|--------|------|-------|
| 0 | 1 | opcode (0x80) |
| 1 | 1 | pad (0x00) |
| 2 | 2 | pad |
| 4 | 4 | opSize (16) |
| 8 | 4 | descriptor: ((col & 0xFF) << 16) \| ((row & 0xFF) << 8) \| (direction & 0xFF) |
| 12 | 4 | config (0x00010100 = start sync, 0x01010100 = end sync) |

From `fresh_insts.bin`: sync occurs on columns 2–6, row 0. Pairs of SYNC commands bracket computation phases.

### 4.11 GEMM Dataflow (from `fresh_insts.bin`)

The 8-column × 2-row (row 0 = memtile, row 1 = core) layout:

```
Columns: 0  1  2  3  4  5  6  7
Row 0:   A  A  A  A  -  -  -  -     (A matrix: 4 columns, 128KB each)
Row 6:   B  B  B  B  B  B  B  B     (B matrix broadcast: 8 columns)
         C  C  C  C  C  C  C  C     (C output: each tile gets a slice)
```

- 4 A-input columns (col 0–3, row 0, BD0 at `0x0001d000`): each BD carries 128KB (0x20000 bytes)
- 8 B-input columns (col 2–6 and more, row 6, BD0 at `0x0601d000`): each BD carries 8KB (0x2000 bytes)
- 8 C-output columns (col 0–12, row 6): BDs staggered at `0x20` intervals within each tile's BD queue
- WRITE commands at offset 0xd100+ program core control registers (tile enable, wakeup, etc.)
- 16 SYNC pairs bracket computational phases

The DDR_PATCH mapping:
- arg=0 → A buffer → row 0 tiles, offset = col * 0x200000 (2MB per column)
- arg=1 → B buffer → row 6 tiles, offset = tile * 0x80000 (512KB per tile)
- arg=2 → C buffer → row 6 tiles, offset = tile * 0x80 bytes (output slice)

### 4.12 Generator Interface

The Layer 2 builder (`npu_instr_gen.py`) takes:

```
Inputs:
  M, K, N           : GEMM dimensions
  tile_m, tile_k, tile_n : tile sizes (defaults from known-working: 32×128×32)
  dma_addr_a        : GEM DMA address of A buffer (for patching)
  dma_addr_b        : GEM DMA address of B buffer
  dma_addr_c        : GEM DMA address of C buffer
  num_cols          : columns to use (default from header)
  num_rows          : rows to use

Output:
  bytes             : complete instruction buffer for submission
```

The generator:
1. Builds header with tile dimensions matching the xclbin layout
2. Creates BD descriptors for each tile with correct buffer_length / control / dma_config patterns
3. Creates DDR_PATCH entries matching the known arg_idx → buffer mapping
4. Creates WRITE entries for core control register programming
5. Creates SYNC entries to bracket computation
6. Returns the byte array for direct submission

## 5. Implementation Plan

### Phase 1a: Parse → Parameterize → Generate

1. Extend `instr_compiler.py` to accept M×K×N parameters
2. Generate instruction buffers for different sizes using the `fresh_insts.bin` pattern
3. Submit via `npu_raw_submit.c` and verify output against CPU GEMM reference
4. Build automated test harness

**Deliverable:** `npu_instr_gen.py` producing verified-correct GEMM kernels.

### Phase 2: Chess VLIW Integration

1. Compile reference GEMM kernels with Chess/Peano to get tight VLIW `.text` sections
2. Extract the VLIW instruction bytes from the Chess `.o` files
3. Replace the tile program memory section in our instruction buffer with Chess-generated code
4. All DMA/BD/sync commands remain from the known-working template
5. Verify correctness matches Phase 1a reference

### Phase 3: Raw VLIW Assembler

1. Build a Python library that encodes AIE2P VLIW 128-bit bundles from symbolic mnemonics
2. Support the 10-15 most common instruction forms (mova, movxm, vmac.f, vlda, vst, vconv, etc.)
3. Hand-write the GEMM inner loop matching Chess's software-pipelined `vmac.f` chain
4. Iterate until byte-for-byte match with Chess output, then generalize

## 6. Verification Strategy

Every generated kernel is verified against CPU-computed reference:

1. Generate random A (M×K), B (K×N) matrices with BFP16 values
2. Compute reference C = A × B on CPU (float32)
3. Build instruction buffer for M×K×N
4. Submit via DRM, read C from output GEM buffer
5. Compare NPU output vs CPU reference with tolerance (BFP16 ≈ 2-3 ULP)
6. Record: correctness (pass/fail), GFLOPS, tile utilization

## 7. Success Criteria

- **Phase 1a:** Parameterised GEMM generator producing correct results at any M×K×N with known-working tile dimensions. Automated test harness passing.
- **Phase 2:** Chess-integrated kernels matching Phase 1a correctness. Measured GFLOPS improvement.
- **Phase 3:** Raw VLIW assembler producing kernels byte-identical to Chess output on known test cases. Then outperforming Chess on new cases.

## 8. Non-Goals

- Modifying the NPU kernel driver or firmware
- Column count bypass (8 columns is the physical limit)
- Replacing the IRON/MLIR toolchain for general use
- DeepSpec training pipeline on NPU (data prep still requires GPU for target cache)
- NPU kernel module compilation or replacement
